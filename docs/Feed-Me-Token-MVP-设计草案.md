# Feed Me Token：MVP 设计草案

> 状态：讨论稿 v0.7（2026-09-28）。MVP 数据源为 Codex，技术栈为 Tauri 2 + Rust + TypeScript/PixiJS；主角与远程攻击方向已确认。Cursor 和 WorkBuddy 列入下一阶段。

## 1. 一句话定义

一个常驻桌面的像素风自动战斗小宠物：它把本机 coding agent 新产生的 token 用量变成“能量棒”，吃掉能量棒攻击入侵怪物，获得金币与经验，再用金币升级攻击。

首版的价值是让真实的 agent 使用与角色成长产生直观联系，同时保持安静、轻量、可随时关闭。

## 2. 设计判断

| 想法 | MVP 判断 | 原因 |
| --- | --- | --- |
| 定时获取 agent token | MVP 仅内置 Codex 适配器，参考 ccusage 的 Codex 读取方式 | 先把增量与去重做可靠；Cursor 和 WorkBuddy 在下一阶段研究并接入。游戏运行时不调用或捆绑 ccusage。 |
| token → 能量棒 | 保留，按新增用量结算 | 历史用量一次性灌入会破坏初次体验；累计数必须去重。 |
| 吃能量棒后战斗 | 保留，作为核心反馈 | 这是游戏识别度最高的动作。 |
| 横版战斗、怪物、升级 | 保留一个极简自动循环 | 首版要证明循环好玩，不先做地图、技能树和复杂战斗。 |
| 角色与敌人 | 原创三头身类人角色，对阵显示器头的人形机器人 | 保留“吃能量棒”的记忆点；具体轮廓、服装、配色和动画需原创。 |
| 多角色、多怪物、多资源 | 延后 | 会分散对数据接入和核心反馈的验证。 |

## 3. 建议的首版体验

1. 用户启动应用；一个无边框、透明背景的小场景浮在桌面边缘。托盘菜单可以打开设置、隐藏场景或退出。
2. 首次运行检测本机 Codex 用量记录。应用显示连接状态和“启用后新增 token”。首次读取只建立基线，游戏计数从 0 开始，不导入历史用量。
3. 每 60 秒读取一次新用量。新增 token 累积达到兑换门槛时，场景里出现能量棒；不足一根的余数留到下一次。
4. 角色自动吃一根能量棒，伸手发射短促能量射线，右侧机器人屏幕出现像素乱码与受击闪烁。没有能量棒时，角色待机，怪物停在攻击范围；游戏不强迫用户为战斗额外消耗 token。
5. 击败怪物获得金币与经验。经验自动提升等级；金币可手动购买一项攻击升级。新怪物继续出现。
6. 关闭或重启应用后，游戏进度和 token 结算进度保持一致；同一条用量不会重复发奖。

### 暂定数值（用于原型验证，可调整）

| 项目 | 初始值 |
| --- | ---: |
| 兑换 | 每 1,000 个新增 token → 1 根能量棒，余数结转 |
| 攻击 | 消耗 1 根能量棒，造成 1 点伤害 |
| 怪物 | 初始 1 点生命；每 20 波生命 +1 |
| 击败奖励 | 1 金币、3 经验 |
| 等级 | 升级所需经验 = 当前等级 × 10；等级在 MVP 中体现成长记录 |
| 攻击升级 | 花 5 金币使伤害 +1；下次价格递增 |

数值的目的仅是让一段正常 agent 工作后能看见一次完整战斗。正式定值应通过可控模拟输入和试玩调整，不能鼓励无意义地消耗 token。

## 4. MVP 范围

### 必做

- Windows 与 macOS 桌面应用：透明无边框窗口、置顶开关、拖动位置、托盘隐藏/退出、静音开关。
- 一名原创三头身类人 2D 像素角色、一种显示器头的人形机器人怪物、待机/吃/攻击/受击或消失等最低限度动画。
- 自动战斗：怪物入场、攻击、击败、奖励、下一波；无复杂操作要求。
- 游戏内置 Codex 用量读取模块；自动发现本地记录、定时读取、增量结算、错误状态提示、手动刷新。
- 游戏状态本地保存；重启后既不重复发奖，也不丢失已获得的能量、金币、经验和升级。
- 简单设置与状态面板：Codex 连接状态、最近刷新时间、启用后新增 token、待用能量棒、数据读取错误。
- 开发用模拟数据入口，用来验证循环；正式运行默认关闭，模拟数据不得混入真实结算记录。

### 暂不做

- 账号、登录、云同步、排行榜、付费、广告。
- 读取聊天内容或提示词；收集成本、模型价格或 API 密钥。
- 多角色、装备、技能树、关卡地图、Boss、每日任务。
- 在 MVP 中读取 Codex 以外的来源，或导入历史 token。
- 失败惩罚、角色死亡、离线战斗模拟。

## 5. 数据方案

以 [ccusage](https://github.com/ccusage/ccusage) 的 Codex 来源实现为参考，在游戏代码里实现自己的 Codex 读取模块。只实现游戏需要的 token 数值，不实现 ccusage 的成本、价格、报表或 CLI。游戏运行时不依赖 ccusage 可执行文件、npm 包或联网下载。如直接借用其代码片段，须按其 MIT 许可证保留相应声明；仅参考数据格式和算法时，记录参考来源即可。

MVP 的来源接口预留 `discover / readNewUsage / health` 等能力，但只交付一个 Codex 实现。Cursor 和 WorkBuddy 不复用或假设 Codex 的文件格式；下一阶段先验证其本地记录或官方接口能否准确提供 token 数据，再分别实现适配器。

Codex 适配器负责发现本地记录路径、只读解析记录，并输出统一的 `来源 + 记录标识 + 时间 + token 分类`。这里的 Codex 包含桌面应用与 CLI；技术小样要分别核实两者在 Windows/macOS 上可读取的用量记录与去重关系。若同一会话反复报告累计数，适配器先还原实际新增量。结算器按稳定标识去重，保存已结算进度；记录被重写、文件回退或跨日时不能重复发奖。输入、输出、缓存 token 的具体兑换口径在数据接入小样中记录并测试；对玩家显示实际采用的统计口径。

- 只读取本机已有记录；默认不上传任何用量数据。
- 首次启用时为当时可见的 Codex 记录保存当前基线；游戏 token、能量棒、金币和经验均从 0 开始。之后运行期间和应用关闭后的新增记录可补结算。
- 数据缺失、文件写入中或格式变化时保留上次进度并显示状态，不凭估算发奖。
- 文件增量或累计值可能被改写；结算须具备幂等性，不能因为刷新、重启或同一来源重复发现而翻倍。
- 来源接口保持独立，便于下一阶段加入 Cursor 和 WorkBuddy；MVP 状态面板只展示 Codex。

## 6. 窗口与画面

窗口暂定约 640×320，角色和怪物以整数倍最近邻方式绘制。角色在左、怪物从右入场；顶部不设常驻 UI，拖动场景可移动窗口。能量棒、金币、等级、升级入口和窗口功能按钮集中在下方两行，详细 token 状态放在可展开面板。

主角是一名原创的贪吃可爱三头身小女孩：吞入带数据纹理的能量棒，腮帮鼓起，伸手发射短促能量射线。敌人是原创的显示器头人形机器人，命中时屏幕出现像素乱码，表现“被破解”。参考形象只提取“圆润、贪吃、吃电子物品”的气质，不使用现有作品的名字、轮廓、服装或标志性细节。具体方案见 [角色美术设定](./Feed-Me-Token-角色美术设定.md)。

### MVP 美术资源清单（建议）

| 类别 | 首版资源 | 制作方式 |
| --- | --- | --- |
| 场景 | 一条可平铺的地面/平台、少量道具和地面阴影；窗口其余区域透明 | 手工像素图或程序绘制；避免大面积不透明背景遮住桌面。 |
| 主角 | 一个面向右侧的贪吃可爱三头身小女孩；待机、吃棒、攻击、胜利各一组动画 | 先定正面/侧面设定图，再逐帧绘制，导出透明 PNG 精灵表。 |
| 敌人 | 一个显示器头人形机器人；入场、待机、受击、消失各一组动画，屏幕表情可换 | 逐帧绘制主体，表情可拆成独立图层复用。 |
| 物件 | 能量棒（场景中与 HUD 各一版）、金币、经验光点 | 小尺寸像素图，尽量让形状区别明显。 |
| 特效 | token 到达、吞食碎屑、手掌蓄光、短促射线、屏幕乱码与命中闪光、奖励飞出、升级 | 先用程序粒子/几何图形制作，仅给重要动作补精灵帧。 |
| UI | 常驻 HUD、升级按钮、来源状态、可展开设置面板、应用与托盘图标 | HUD 图标用像素图；面板和中文文字用 HTML/CSS，保证高 DPI 下清楚。 |

工作量粗估：一套平台场景；主角约 16–24 帧、敌人约 12–16 帧；4–6 个物件图标；6 类轻量特效；一套 HUD 和设置面板。帧数以动作可读为准，不作为必须填满的数量指标。

主角约 48–60 逻辑像素高，头身比例约 1:2；敌人与主角体量接近。角色采用清晰外轮廓与少量阴影层级，使浅色、深色桌面壁纸上都能辨认。常驻画面保持低信息密度：左侧主角、右侧敌人、底部窄平台，资源数字集中在下方控制栏。

美术方向为“复古终端里的小食客”：主角以暖白/青绿为主色，能量棒用琥珀色强调“可吃”，机器人以深蓝灰和少量警示红区分。小女孩的识别点是夸张的期待、咀嚼和满足表情，具体服装、脸部特征和配色可在概念稿中微调。

### 美术生成与交付流程

1. 写一页风格规范：角色轮廓、三头身比例、有限色板、像素尺寸、描边与阴影规则。
2. 用图像生成或草图做 2–3 张**原创概念稿**，比较角色气质与显示器头机器人的关系；不直接把概念图缩小当游戏精灵。
3. 在 Aseprite/LibreSprite 等像素画工具中重绘标准站姿和关键动作。动画的关键帧由同一套角色结构制作，避免逐帧 AI 生成带来的比例漂移。
4. 导出透明 PNG 精灵表及帧尺寸/时长数据；保存可编辑源文件。游戏使用最近邻放大，避免像素边缘模糊。
5. 在 Windows 与 macOS 上用浅色、深色桌面背景和常见缩放比例检查可读性、透明边缘及动画节奏。

先用自制简化精灵接通完整战斗循环；正式美术替换时维持相同动作命名和锚点。UI、图标和特效也保留可编辑源文件与来源记录。

## 7. 技术实施方案（已确认）

采用 Tauri 2 + Rust Codex 读取模块 + TypeScript + PixiJS。Tauri/Rust 负责窗口、托盘、本地文件读取和保存；TypeScript 负责界面与战斗状态机；PixiJS 负责像素精灵和特效渲染。渲染层不直接访问用户文件。窗口隐藏时停止绘制，长时间待机时降低动画更新频率。

必须先做 Windows 和 macOS 的技术小样：透明置顶窗口、拖动与托盘、Codex 记录读取、锁屏/睡眠后恢复。当前工作环境是 Windows；macOS 行为需要在真实 Mac 上验收。数据存为应用私有目录中的小型本地状态文件，采用原子写入和备份。

建议按以下顺序实施，每一步都能独立验收：

1. 双平台技术小样：验证透明窗口、托盘与 Codex 原始记录，确认增量、跨日、重启和错误处理。
2. 桌面外壳：透明窗口、位置保存、托盘、设置与状态面板。
3. 最小战斗循环：模拟能量棒输入驱动吃、攻击、奖励、升级。
4. 接通 Codex 数据、完成状态持久化和双平台打包测试。
5. 调整数值、动画与闲置时资源消耗，完成首版验收。

## 8. MVP 验收条件

- 在本机 Codex 产生新用量后，无需手动录入，应用能在下一次刷新后显示新增 token，并按门槛结算能量棒。
- 连续刷新和重启后，同一用量只兑换一次；不足一根的余数保留。
- 玩家可看见“吃棒 → 攻击 → 击败 → 获得金币/经验 → 升级 → 下一只怪物”的完整循环。
- 没有新用量、来源不存在或读取失败时，应用可继续运行且清楚显示原因。
- 窗口可移动、隐藏和退出；游戏进度在重启后恢复。
- 禁用网络时，已有本地记录的读取和战斗仍可工作。
- Windows 和 macOS 发行包均独立读取本机 Codex 记录；用户无需单独安装 Node 或 ccusage。
- Codex 适配器有样本记录和增量去重验收；未检测到 Codex 记录时游戏仍可启动并显示来源状态。

## 9. 决策状态

- 已确认：MVP 只内置 Codex 用量读取；下一阶段研究并支持 Cursor、WorkBuddy；Windows + macOS；原创三头身类人角色和显示器头人形机器人敌人；首次启用从 0 开始，不导入历史数据；采用 **Tauri 2 + Rust + TS/PixiJS**。
- 已定主角气质与战斗动作：贪吃可爱的三头身小女孩，伸手发射短促能量射线；服装与细节先按角色美术设定制作概念稿，再据图定稿。
- 数据口径待技术小样验证：Codex 记录中的 token 字段及缓存 token 是否计入兑换。

正式的 [MVP 实施文档](./Feed-Me-Token-MVP-实施文档.md) 已形成，当前原型与剩余验收状态以该文档为准。

## 10. MVP 后的来源扩展

下一阶段优先研究并接入 Cursor 和 WorkBuddy。每个来源先确认产品版本、Windows/macOS 的记录位置或官方接口、是否提供真实 token 数值、时间戳及缓存 token 口径，再决定读取方式。若只提供请求次数或金额，不把它估算成“真实 token”展示或兑换。通过可行性验证后，沿用 MVP 的来源接口、首次启用基线和去重结算规则接入。
