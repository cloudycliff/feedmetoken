## 维护方式

每次修改玩法、数值、UI、数据读取、存档、平台支持或美术方案时，在同一次提交中追加一条变更记录。记录以下五项，未涉及的项目写“无变更”，未测试的项目明确写“未验证”：

1. **缘由与决策**：用户需求或发现的问题；旧规则 → 新规则；选择该方案的原因。
2. **实现**：改了哪些模块、数据格式或交互，已有存档如何处理。
3. **验证**：实际执行的构建、测试和人工检查及其结果，区分浏览器预览和原生窗口。
4. **遗留**：尚未实现或尚未验证的行为。
5. **文档同步**：当前规则变化时更新实施文档；用户可见行为变化时更新仓库 README。

新记录按时间倒序写入“变更记录”。不要修改旧记录来掩盖决策变化；如旧结论有误，追加更正。每次变更后更新下方“当前实现状态”。

## 决策记录

### D-001：MVP 范围与技术栈（2026-09-28，生效）

- MVP 仅支持 Codex；Cursor 与 WorkBuddy 排在下一阶段。应用参考 ccusage 的读取思路，不依赖其程序或包。
- 首次启用从零结算，不导入历史用量；目标平台为 Windows 和 macOS。
- 技术栈为 Tauri 2 + Rust 读取/存档 + TypeScript/PixiJS 画面。主角是原创三头身贪吃小女孩，敌人是显示器头机器人。
- 主角吃能量棒后伸手发射短射线，机器人命中时屏幕乱码。参考作品只用于气质讨论，不沿用角色设计。

### D-002：控制栏移至下方（2026-09-28，生效）

- **旧方案**：顶部标题栏放品牌、状态和功能按钮；底部只放资源与升级。
- **新方案**：顶部不设常驻 UI；底部两行容纳资源、升级、状态、刷新、详情、置顶、静音、最小化与关闭。拖动战斗场景移动窗口；最小化进入系统最小化状态，关闭直接退出游戏，托盘“显示”可恢复最小化窗口。
- **原因**：减少画面上方遮挡，并补齐无边框窗口的基本控制。

### D-003：敌人入场与快速更替（2026-09-28，生效）

- **旧方案**：敌人静止在战斗位置；生命为 `3 + floor((波次 - 1) / 10)`，前期需要多次攻击。
- **新方案**：每只机器人从右侧走入，约 1 秒到达射程；入场期间不受攻击。生命为 `1 + floor((波次 - 1) / 20)`，前 20 波默认一击倒下。击败后约 0.3 秒熄屏淡出，下一只随即入场。
- **原因**：让消耗一根能量棒更容易形成“击败 → 奖励 → 下一只”的完整反馈。攻击升级在后续生命增长时仍有作用。
- **存档兼容**：加载旧存档时只将当前敌人生命下调到新波次上限，保留能量、金币、经验和波次。

### D-004：能量棒生产与取用表演（2026-09-28，生效）

- **旧方案**：刷新后库存数字直接增加，地面只显示一根静态能量棒；角色在原地吃棒。
- **新方案**：左侧增加输入管道、生产机和堆放托盘。新增 token 触发输入粒子与机器工作；每满 1,000 token 的产出落入堆里，主角从堆中取棒后吃下。已有库存启动时直接显示，不回放历史。单次大量产出最多逐一表演四根，其余合批入堆；堆图形最多绘制九根，控制栏保留准确库存数字。
- **原因**：让 token 兑换、库存增加和角色消耗之间的因果关系能直接从画面读出。
- **存档兼容**：Rust 兑换与存档格式不变。生产队列只存在于前端画面；关闭期间尚未播完的库存会在下次启动时直接出现在堆中，不会重复兑换或丢失。

### D-005：统一数值配置（2026-09-28，生效）

- **旧方案**：兑换、敌人生命、奖励和升级公式分别写在 Rust 与 TS 逻辑中；动画与预览数值散落在 TS 代码中，调参必须同步多处。
- **新方案**：`app/game-config.json` 统一保存玩法规则、动画节奏、画面数量限制和浏览器预览参数。Rust 与 TS 在构建时读取同一个文件；构建前校验字段和数值。安装版如需新数值，必须重新构建。
- **原因**：避免两端数值分叉，让试玩调参有明确入口和字段说明。默认值与此前行为一致。
- **存档兼容**：格式不变。初始等级、攻击力和波次只影响新存档；兑换阈值变化会按新值继续处理旧余数；敌人当前生命加载时仍按新波次上限下调。正式调这些数值前需确认迁移策略。

### D-006：内置皮肤资源包（2026-09-29，生效）

- **旧方案**：主角、机器人、生产机、能量棒、托盘与平台由 `main.ts` 的 PixiJS `Graphics` 直接绘制，美术必须改绘制代码。
- **新方案**：这些对象从透明 PNG 图集加载，`catalog.json` 列出内置皮肤，各皮肤 `manifest.json` 定义帧、动作、锚点和特效颜色。状态面板可切换“薄荷机房”和“蜜桃终端”两套占位皮肤；射线及输入粒子保留程序绘制。用户导入外部皮肤暂不纳入 MVP。
- **原因**：先建立换图契约，后续制作正式美术时可以替换资源和清单，不必重写生产及战斗规则。
- **存档兼容**：原生存档新增 `skinId`，旧存档默认 `mint`；浏览器预览用本地存储保存选择。皮肤选择只改外观，不改 token、库存、波次或奖励。资源不可用时回退默认皮肤。

### D-007：采用主角概念稿 v1（2026-09-29，生效）

- **旧方案**：两套皮肤中的主角均为简化占位像素小人，角色特征不足。
- **新方案**：以用户认可的[主角概念稿 v1](./art/hero-v1-concept.png)为造型依据，保留圆脸鼓腮、深色短发与翘发、宽松外套、零食袋和琥珀色包装棒。重绘为同帧槽的九个像素动作姿势，两套皮肤保留各自配色。概念稿不直接缩小作为运行资源。
- **原因**：把已认可的角色识别元素转化为桌面小尺寸中可读的动作，作为后续完善美术的基线。
- **存档兼容**：图集、动作帧和前端表演变更；皮肤 ID、玩法数值、Codex 读取与存档格式不变。已有存档自动看到新版主角。

### D-008：增加设定图待机小样（2026-09-29，试验中）

- **旧方案**：只有两套像素皮肤；概念图仅作离线参考，无法在游戏场景中判断非像素风格。
- **新方案**：增加“插画小样（待机）”皮肤。概念图抠成透明 PNG，在待机时按约 78 逻辑像素高显示；取棒、吃棒和攻击仍使用薄荷像素帧。画布保持 320×128 逻辑坐标，但以 2 倍分辨率渲染；像素图集最近邻采样，插画线性采样。
- **原因**：先在实际生产机和机器人旁比较设定图的比例、清晰度与风格，再决定是否制作整套非像素动作和场景资源。
- **存档兼容**：第三套皮肤沿用现有 `skinId` 字段；数值、Codex 数据、战斗状态机和存档格式不变。旧存档的薄荷或蜜桃选择保持不变。

### D-009：第三套皮肤扩展为完整插画动作（2026-09-29，生效）

- **旧方案**：第三套皮肤只在待机显示非像素插画；取棒、吃棒与攻击切回薄荷像素帧。
- **新方案**：第三套更名为“插画动作版”。以主角 v1 造型生成六姿势非像素图集，覆盖空手待机、俯身取棒、咬棒、鼓腮、伸手发射与胜利擦嘴；受击阶段沿用发射姿势。动作全程保持插画主角。取棒终点和射线起点随皮肤清单配置。
- **原因**：用户选定非像素方向并要求把其余动作也改成这一风格；原方案在战斗时发生明显的像素与插画跳变。
- **存档兼容**：`concept` 皮肤 ID 与玩法存档格式保持不变；已选择第三套皮肤的存档自动显示新版动作。旧资源清单中的 `idleIllustration` 格式改为 `illustration` 动作图集格式，外部资源包若自行沿用旧格式需迁移。

### D-010：第三套皮肤的机器人改用插画动作（2026-09-29，生效）

- **旧方案**：第三套皮肤的主角全程使用非像素插画，机器人仍沿用薄荷像素帧，战斗双方风格不一致。
- **新方案**：显示器头机器人使用走入、待机、屏幕乱码受击和关机四姿势透明插画图集。射线命中屏幕的位置由皮肤清单配置；薄荷与蜜桃皮肤继续使用原有像素机器人。
- **原因**：接着统一战斗双方的角色风格，使入场、命中和更替过程都能看到同一造型。
- **存档兼容**：皮肤 ID、玩法数值、Codex 读取和存档格式不变；已选择第三套皮肤的存档自动显示新版机器人。

### D-011：插画动作版成为默认皮肤（2026-09-30，生效）

- **旧方案**：皮肤目录、新存档及缺少 `skinId` 的旧存档都默认 `mint`。覆盖安装会保留存档，因此原生程序继续显示像素角色。
- **新方案**：上述默认值统一改为 `concept`；显式保存的 `mint`、`peach` 或 `concept` 仍按原选择显示。生产机与场景继续使用现有像素占位资源。
- **原因**：用户已选择非像素角色方向，并反馈覆盖安装后仍看到旧像素造型；默认皮肤与已选美术方向不一致。
- **存档兼容**：不改存档结构、用量和游戏进度；仅对缺少皮肤字段的旧存档改变默认外观。版本升至 0.1.1，便于辨认新安装包。
